code got materially better; the release and deployment surface turns out to be

### 1.2 What the execution did unusually well

**It treated the brief as a hypothesis.** Eight of eight items carry substantive
corrections, several load-bearing. [§2.4](2026-09-15.md#24-add-parser-robustness-tests-and-a-depth-cap-row-10)
is the one that matters most: following the brief literally would have shipped a
depth guard that passed its own tests while leaving the overflow reachable
through the commonest pathological shape. That correction required reading
`parseBp`'s `for(;;)` loop and understanding why parser-recursion depth and AST
depth diverge — not something a brief-follower finds.

**Guards were mutation-tested, not merely written.** Five PRs broke the thing
the new check protects and confirmed the check went red: dropping `\x7f` from the
control-character class and reordering the drive-letter test ([#92](https://github.com/michal-niedzwiedzki/visimark/pull/92)),
restoring the old `writeFileSync` ([#93](https://github.com/michal-niedzwiedzki/visimark/pull/93)),
treating `^` as left-associative ([#94](https://github.com/michal-niedzwiedzki/visimark/pull/94)),
perturbing a literal in `browser-entry.ts` ([#95](https://github.com/michal-niedzwiedzki/visimark/pull/95)),
and deleting the `default:` line so the `awk` extraction fails loudly instead of
going permanently green ([#97](https://github.com/michal-niedzwiedzki/visimark/pull/97)).
A guard that has never been observed to fail is a guard nobody has tested, and
this chain knew it.

**Scope was declined where declining was right.** [#94](https://github.com/michal-niedzwiedzki/visimark/pull/94)
refused to make five recursive walkers iterative; [#98](https://github.com/michal-niedzwiedzki/visimark/pull/98)
refused to split `build()`'s sheet passes and said why; [#92](https://github.com/michal-niedzwiedzki/visimark/pull/92)
left [§2.3](2026-09-15.md#23-close-the-toctou-window-in-the-path-gates-row-6)
untouched because the brief said to ask first. Known trades were pinned with
tests citing the decision rather than left to be rediscovered as bugs — the
300-column `SUM` chain in [#94](https://github.com/michal-niedzwiedzki/visimark/pull/94)
is the model case.

**The paper trail is complete.** Eight plan documents in [docs/design/](../design/),
every §-status updated, `SECURITY.md` Scope extended with the residual window
and what would change it, `error.code: "WRITE"` recorded as the spec change it
was. Tests went 680 → 771 with every refactor verified byte-for-byte.

### 1.3 Where it fell down

**Nothing ran the playground.** [§2](#2-the-regression) below.

**Nobody looked at the release.** The first review rated release automation
**A** — "auto-closes shipped issues with ancestry checks". Nine PRs and a full
day of review work later, the v0.1.3 release run had been red since 07:24 that
morning, and no one in the chain checked. See [row 1](#31-findings) — this is
the most consequential thing in this document.

**Self-certification without a second pair of eyes.** All nine PRs merged with
zero review comments and zero review approvals. The self-certification is
unusually good, which is why it mostly held — and [#99](https://github.com/michal-niedzwiedzki/visimark/pull/99)
is the proof that "unusually good" is not "sufficient".

**Verification numbers drift between PR bodies.** 758, then 711 ("700 before"),
then 753, now 771 — because the scope silently alternated between `bun test`
at the root and `bun test packages/visimark`. Every individual claim is true;
read in sequence they look like tests disappearing. Say which command produced
the number.

**A−.** The analytical quality is the top of what this kind of work gets: the

The response was good: reproduce, fix, add the test that would have caught it,
verify the test fails on the pre-fix commit. What it did not do is close the

### 4.1 Make the release pipeline fail loudly and recoverably (row 1)

**Rating: D — a shipped release is incomplete and nothing said so.**

#### The state, verified

Run [34941523701](https://github.com/michal-niedzwiedzki/visimark/actions/runs/34941523701),
tag `v0.1.3`, one attempt, `failure`:

| Step | Result |
|---|---|
| Publish the engine to npm | success — npm `dist-tags.latest` is `0.1.3` |
| Publish to the VS Code Marketplace | **failure** — `Access Denied: … needs … Publish new extensions to an existing publisher` |
| Publish to Open VSX | **skipped** — the API still returns `0.1.2` only |
| GitHub Release | **skipped** — the `v0.1.3` release exists, cut by hand at 07:23 |
| Close shipped request issues | **skipped** |

Consequences: Open VSX users are a release behind with no signal; the
Marketplace leg needs a credential fix (the wording says VS Code treated this as
a *new* extension, though `v0.1.2` published successfully on 2026-09-10 — check
whether the extension was delisted or the PAT rotated/rescoped);
[#66](https://github.com/michal-niedzwiedzki/visimark/issues/66) and
[#70](https://github.com/michal-niedzwiedzki/visimark/issues/70) remain open
with their features shipped.

#### What to do

**1. Repair v0.1.3 first**, before any workflow change. Fix the PAT, publish the
extension to both registries, close the two issues with the same wording the
workflow uses.

**2. Stop one leg stranding the others.** The legs are already idempotent — that
is the whole point of the existence queries the first review praised — so
failing the job at the first error buys nothing and costs the bookkeeping. Let
each publish leg record its outcome and run the later steps regardless, then
fail the job at the end if any leg failed. `if: always()` on the steps that do
not depend on the extension, plus a final gate, is enough. Do not weaken any
leg's *own* error handling: "an unexpected failure has to fail the job, not be
mistaken for a no-op" stays true.

**3. Make `workflow_dispatch` able to do what the header promises.**
[release.yml:6-8](../../.github/workflows/release.yml#L6-L8) says manual runs
"backfill whatever is missing", but *GitHub Release* and *Close shipped request
issues* are gated on `startsWith(github.ref, 'refs/tags/')` and a dispatch has
no tag ref. Either add a `tag` input those steps can use, or correct the
comment. A documented recovery path that silently does two-thirds of the job is
worse than one that says what it skips.

**4. Notice next time.** A red release currently looks exactly like a green one
from inside the repo. The cheapest signal is a final step that queries all three
registries for `$ENGINE_VERSION`/`$EXT_VERSION` and fails if any is missing —
the same "ask the registry, don't trust the exit code" discipline already used
per-leg, applied once at the end as an assertion rather than a branch.

#### Constraints

- Keep every existence query. They are the reason a re-run is safe.
- The issue-close ancestry logic is correct and subtle (`git merge-base
  --is-ancestor` against both this tag and the previous one, with "issue still
  open" as the idempotency guard). Do not rewrite it; only change when it runs.
- `fetch-depth: 0` is load-bearing for that step.

### 4.2 Keep `node:fs` out of the browser graph (row 3)

**Rating: C+ — [#99](https://github.com/michal-niedzwiedzki/visimark/pull/99) closed the instance, not the class.**

#### The problem

`browser-entry.ts`'s header says the bundle exposes the pipeline with "no
node:fs". That is not true of the module graph: `check` → `checkCharts` →
`artifact/stale.ts`, `fs/gate.ts`, `import/resolve.ts` → `fs/open.ts`. The
shipped bundle contains `existsSync`, `realpathSync`, `openSync` and
`createHash`, all resolving to `(()=>({}))`.

Nothing throws today, for two reasons, neither of them a boundary:

- `checkCharts` and `resolveImports` each return early on `opts.docPath ===
  undefined`, which is the browser's situation. This is deliberate, commented,
  and good — but it is an invariant held by convention, not by types or module
  structure.
- `realpathSyncSafe`'s `try/catch`, written for "this path does not exist yet",
  also swallows "`realpathSync` is not a function". A stub failure is being
  absorbed by error handling aimed at something else.

And the invariant is publicly breakable: `fmt(source, opts)` is exported to
`window.VisiMark` and forwards `opts.docPath` straight into `check`. Today
[playground.html:2076](../playground.html) calls `VM.fmt(source, {})`. One
caller passing a path reproduces [#99](https://github.com/michal-niedzwiedzki/visimark/pull/99)'s
crash exactly.

#### What to do

Pick one and commit to it:

**Option A — a port.** Give the filesystem-touching phases an injected reader
interface, defaulting to the `node:fs` implementation and absent in the browser
build. The `docPath === undefined` checks become "no reader was supplied", which
is the same condition stated structurally. This removes `node:fs` from the
browser graph entirely and drops bundle size.

**Option B — make the invariant explicit and tested.** Keep the current
structure, but say in `browser-entry.ts` that the browser build's correctness
rests on never supplying a `docPath`, narrow the browser `fmt` export so the
option is not reachable, and add tests asserting that every browser-reachable
entry point leaves the `node:fs` call sites untouched.

A is the real fix; B is honest and cheap. Do not leave it where it is, which is
neither.

Separately, narrow `realpathSyncSafe`'s `catch` so a missing function is not
mistaken for a missing file.

#### Constraints

- **No behaviour change to the CLI.** `bun test` stays at 771, and `check` /
  `fmt` / `explain` output stays byte-identical across every `docs/example-*.md`.
- The bundle must stay byte-deterministic under Bun 1.4.2 — `playground-bundle`
  compares exactly.
- Keep [playground.test.ts](../../packages/visimark/test/playground.test.ts)
  passing; it is the regression test for [#99](https://github.com/michal-niedzwiedzki/visimark/pull/99).
- The `docPath === undefined` comments in `check-charts.ts` and `resolve.ts`
  explain a real decision. Carry the reasoning across rather than deleting it.

### 4.3 Stop the playground failing its own imports chapter (row 4)

**Rating: C — live, user-visible, on the last chapter of the tutorial.**

#### The problem, reproduced

Load `13-imports.md` in the playground. The check panel reads:

```
13-imports.md

  UNDEF   order.grand_total  unknown name `Total`
          did you mean `grand_total`?

  1 problem (0 stale, 1 error)
```

The CLI on the same file reports `0 problems`. The suggestion is nonsense —
it proposes that `grand_total` refer to itself.

`resolveImports` marks the sheet `skipped` when there is no `docPath` and
reports nothing, with a comment saying it "mirrors chart handling". It mirrors
the *silence* but not the *suppression*: `checkCharts` returns a `skipped`
chart and no finding, and nothing downstream depends on a chart. A skipped
import leaves every column the CSV would have supplied undefined, so the
sheet's own bindings fail with `UNDEF` — and `did you mean` then runs its
Levenshtein suggestion over a name set missing the imported columns.

The chapter is the tutorial's finale and carries the "Data Importer" badge. Its
quest text says *"only `grand_total = SUM(Total)` runs here"*. It does not run.

#### What to do

Either is defensible; **prefer the second** if the playground's file store makes
it cheap.

### 4.4 Derive the headroom script's cap (row 5)

**Rating: B− — small, and exactly the drift class this repo just built a guard for.**

#### The problem

[parser.ts:69](../../packages/visimark/src/lang/parser.ts#L69) declares
`MAX_EXPR_DEPTH = 256`. [stack-headroom.mjs:25](../../scripts/stack-headroom.mjs#L25)
declares `const CAP = 256` with *"Must match MAX_EXPR_DEPTH"*. Nothing checks
it. Lower the real cap to 128 and CI keeps certifying headroom for 256 — and
the check's own failure message advises lowering the cap further, which would
widen the gap it cannot see.

This is the same shape as the `action.yml` default that
[#97](https://github.com/michal-niedzwiedzki/visimark/pull/97) fixed hours
earlier: a number that must equal another number, maintained by comment.

#### What to do

Read the constant rather than restating it. The script is plain ESM run by both
`bun` and `node`, and `parser.ts` is TypeScript that neither can import
directly, so a small extraction is the pragmatic route — the same `awk`-style
reasoning [#97](https://github.com/michal-niedzwiedzki/visimark/pull/97) applied
to `action.yml`, including its most important detail: **an extraction that stops
matching must fail loudly, not read as zero.** [#97](https://github.com/michal-niedzwiedzki/visimark/pull/97)'s
guard is the pattern to copy.

If extraction is judged too clever for a 10-line script, assert instead: a CI
step, or a test in `test/lang/`, that reads both files and fails when the
numbers differ. Either closes it; the comment alone does not.

#### Constraints

- The script must keep running under **both** `bun` and `node` with no
  dependencies, and keep working from a clean checkout.
- Do not change `MIN_RATIO` or the calibration comment. The 2.5× optimism
  factor and the 12,501-frame measurement behind it are the reasoning that makes
  the 10× threshold meaningful.
- `acceptance-node` runs this script; keep its exit codes and message wording.
