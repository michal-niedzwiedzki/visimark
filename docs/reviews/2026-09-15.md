# VisiMark — code review

**Date:** 2026-09-15 · **Commit:** `21d95a0` · **Scope:** whole repository

Reviewed: ~9,722 lines of source across four workspaces (`packages/visimark`,
`packages/visimark-lsp`, `editors/vscode`, plus the docs site), 8,232 lines of
tests (680 passing, 6,414 assertions, 2.85s), the composite Action, and all
five GitHub workflows.

**Overall: A−.** This sits well above typical open-source quality. The
engineering practices — docs executed as tests, CI that verifies runtime
isolation rather than assuming it, and a spec/plan trail that makes design
constraints defensible rather than folkloric — are genuinely unusual. The
weaknesses are concentrated, not diffuse: one oversized function, one broken
artifact-freshness mechanism, and some lint noise.

## 2. Work prompts

Each subsection below is a self-contained brief for an agent picking up that
item with no prior context. They are independent and can be worked in any
order, with one exception noted in §2.1.

### Shared context for every prompt

VisiMark gives Markdown spreadsheet mechanics: a ` ```vmark ` fenced block
declares column rules over a GFM table, and `visimark check` proves the
numbers in the document still agree with the formulas that produced them.

Repository conventions you must honour:

- **Runtime is Bun.** Test with `bun test`, typecheck with `bun run typecheck`,
  lint with `bun run lint`, format with `bun run format`. To exercise the CLI
  use `visimark-dev` or `bun src/cli/main.ts` from `packages/visimark` —
  **never `bunx visimark`**, which silently runs the last published build
  instead of your working tree.
- **`strict` + `noUncheckedIndexedAccess` are non-negotiable.** The codebase
  has zero `any`, zero `as any`, and zero `@ts-ignore`/`@ts-expect-error`. Do
  not introduce the first one. Non-null assertions (`!`) after a bounds check
  are the established idiom and are fine.
- **Comments explain *why*, never *what*.** Match the existing density and
  voice. When you encode a non-obvious decision, say what breaks without it.
- **Design docs are load-bearing.** Features carry a paired
  `docs/design/<feature>-spec.md` and `-plan.md` linked to the deciding GitHub
  issue. Refactors do not need one, but if you change observable behaviour you
  must say so explicitly and stop for the maintainer's decision.
- **Attribution.** Commits keep the maintainer as Git author and credit the AI
  only via a single `Co-Authored-By` trailer naming the model actually running
  this session. See `.claude/rules/ai-attribution.md`. Do not copy a trailer
  out of an old commit or a command file.
- **Conventional commits**, matching the existing history style
  (`fix:`, `refactor:`, `ci:`, `docs:`, `test:`).
- **`bun test` must stay green: 680 tests, 0 failures.** Several tests assert
  CLI output *byte-for-byte* against transcripts embedded in the published
  docs. If you change reporting output at all, those docs must change with it,
  and that is a behaviour change requiring sign-off.

### 2.1 Decompose `check()` (row 3)

**Rating: C — the largest structural debt in the repo.**

**Status: DONE [PR#91](https://github.com/michal-niedzwiedzki/visimark/pull/91)**

#### The problem

`check()` in `packages/visimark/src/eval/check.ts` runs from line 99 to line
1115: **1,017 lines in a single function.** Inside it are roughly 30 mutable
accumulators declared at the top (`values`, `cells`, `unevaluable`,
`columnPrecision`, `scalarPrecision`, `columnUnits`, `scalarUnits`,
`unitConflicts`, `staleScalars`, `dateErrorRows`, `entries`, `assertSuppressed`,
`assertionsHandled`, `assertionResults`, `buildableCharts`, `sheetSeen`,
`claimedPaths`, …), plus four helper functions declared at the *bottom* of the
body (`base`, `readColumn`, `readLabels`, `inputPrecision` at lines 638, 649,
669, 680) that close over those accumulators.

The function is not sloppy — the phases are clearly delimited by comments and
the logic is correct. The problem is that every phase can touch every
accumulator, so there is no enforced boundary anywhere, and the only way to
know what a phase reads or writes is to read all 1,017 lines.

#### The phases, as the existing comments already name them

| Lines | Phase |
|---|---|
| 100–106 | resolve imports, build topological order |
| 107–152 | allocate accumulators, emit carried structural findings |
| 153–202 | infer per-column and per-scalar decoration (units) and precision |
| 205–308 | **main binding evaluation loop** over `order` |
| 310–319 | report dependency cycles |
| 321–347 | assertions unreachable by the topological sort |
| 349–547 | **generated artifacts (charts)** |
| 549–583 | anchors: collapse staleness, flag rewrite-less anchors |
| 585–603 | WARN: scalar defined, never read, never anchored |
| 605–611 | WARN: `is` alias declared, never used |
| 613–636 | order findings, assemble `AssertionResult[]` |
| 636–700+ | helpers bound to the closure |

#### What to do

Introduce an explicit state object rather than a closure:

```ts
interface CheckState {
  readonly model: DocModel;
  readonly opts: CheckOptions;
  values: Map<string, Value>;
  cells: Map<string, (Value | null)[]>;
  // … the rest of the current accumulators
  emit(f: Finding, extra?: FindingExtra): void;
}
```

Then lift each phase to a module-level function taking `CheckState`, so its
inputs and outputs are visible in the signature. `check()` becomes a ~30-line
sequence of phase calls returning `CheckResult`.

**Start with the chart phase (lines 349–547, ~199 lines).** It is the most
decoupled: by the time it runs, its operands have already been resolved and
shape-checked by the binding loop, so it needs only `values`/`cells` for
reading plus `emit`. The four closure helpers at the bottom exist almost
entirely to serve it, so they move out with it into something like
`src/eval/check-charts.ts`. Doing this one first proves the `CheckState`
pattern on the highest-value target with the least entanglement.

Land it as **one phase per commit** so each is reviewable and bisectable.
Do §2.8 only after this, since `cmdExplain` consumes `CheckResult`.

#### Constraints

- **This is a pure refactor. `CheckResult` must not change shape, and not one
  finding — code, message, or ordering — may differ.** Finding order is
  load-bearing: `orderFindings()` at line 1117 sorts by sheet-first-seen and a
  determinism counter (`det`), and the acceptance tests compare CLI output
  byte-for-byte against transcripts inside `docs/example-invoice-drift.md`.
- Verify with `bun test` (all 680 green) **and** by confirming
  `git diff --exit-code` is clean over `docs/` after running
  `bun src/cli/main.ts check docs/example-invoice-drift.md`.
- Do not "improve" behaviour you notice along the way. If you find a bug,
  note it and leave it — a behaviour change hidden in a 1,000-line refactor is
  unreviewable.

### 2.2 De-duplicate the two path gates (row 5)

**Rating: C+ — duplicated security-critical code.**

**Status: DONE [PR#92](https://github.com/michal-niedzwiedzki/visimark/pull/92)**

#### The problem

`packages/visimark/src/artifact/path.ts` (the chart-output write gate) and
`packages/visimark/src/import/path.ts` (the CSV-input read gate) are ~85 lines
each and near-identical. Normalizing away only the noun ("artifact path" vs
"imported file path") and the extension (`.svg` vs `.csv`) leaves ~44 differing
lines, and most of those are comments. `contains()` and `realpathSyncSafe()`
are byte-identical copies.

Both implement the same sequence: reject empty → reject control characters →
reject drive letter → reject URL scheme → reject absolute → require extension →
reject Windows device names → resolve base via `realpath` → check containment →
re-check containment through symlinks on both target and parent.

This is the repo's most security-sensitive code. Two copies means a future
hardening fix lands in one and not the other.

#### What to do

Extract a single shared gate — `packages/visimark/src/fs/gate.ts` is a
reasonable home — parameterised by the two things that genuinely differ:

```ts
export interface GateSpec {
  /** the noun used in every error message, e.g. "artifact path" */
  noun: string;
  /** required lowercase extension including the dot, e.g. ".svg" */
  ext: string;
}
export function gatePath(docPath: string, url: string, spec: GateSpec): PathResult;
```

Both existing modules then become thin wrappers that keep their current
exported names and signatures, so no caller changes. `isSymlink()` stays in
`artifact/path.ts` — only the write side uses it.

#### Constraints

- **Error message strings must not change.** They are asserted in
  `test/artifact/path.test.ts` and `test/import/resolve.test.ts`, and some
  surface in doc transcripts.
- Preserve the **ordering** of the checks exactly. The drive-letter test runs
  before the URL-scheme test on purpose (a `C:` prefix also matches the scheme
  regex) and there is a comment in `artifact/path.ts` saying so — carry that
  comment across.
- Preserve the rationale comments. The "every rule here is a **refusal, never
  a transformation**" paragraph is the design principle behind the whole
  module; it belongs on the shared function.
- The two gates differ in one real respect beyond noun and extension: only the
  **write** side layers a "refuse to overwrite a file without VisiMark's
  metadata marker" rule, and that lives in the caller, not the gate. Confirm
  that stays true.

### 2.3 Close the TOCTOU window in the path gates (row 6)

**Rating: B — a real but low-severity race. Lowest priority; confirm intent first.**

**Status: DONE [PR#93](https://github.com/michal-niedzwiedzki/visimark/pull/93)**

#### The problem

Both gates in §2.2 follow `existsSync(target)` → `realpathSync(target)` →
(return to caller) → `writeFileSync(target)`. Between the validation and the
write, an attacker with write access to the document's directory can replace
`target` with a symlink pointing outside the tree, defeating the containment
check.

#### Why this may not be worth fixing

VisiMark is a local developer CLI. An attacker who can create files in your
repo working directory during a `visimark fmt` run has easier paths to harm.
`SECURITY.md` scopes the threat model to "a document that causes `visimark` to
… read or write files it was not asked to" — a hostile *document* cannot
exploit this, only a hostile *concurrent process*.

**So: ask the maintainer whether to fix or to document-and-accept before doing
the work.** Either outcome is defensible; an explicit decision recorded in a
comment is better than silence.

#### If fixing

Make the write atomic with respect to the check by operating on a file
descriptor rather than re-resolving the path:

- Open with `open(target, 'wx')` for a new artifact — this fails if the path
  exists, so it cannot follow a symlink planted after the check.
- For the overwrite case, `open(target, 'r+')` then `fstat` the descriptor and
  verify it is a regular file (not a symlink or device) before writing through
  it.
- Node's `fs` constants also offer `O_NOFOLLOW`; on Linux and macOS this is the
  most direct expression of the intent. Note it is not portable to Windows, so
  it needs a guarded fallback.

Add a test that plants a symlink between gate and write (a temp dir, a gate
call, then swap the target for a symlink, then the write) and asserts the write
is refused.

#### If accepting

Add a short comment to both gates naming the window, why it is out of scope
given the local-CLI threat model, and what would change that (e.g. if VisiMark
ever runs as a service or in a shared CI workspace). Mention it in
`SECURITY.md` under Scope.

### 2.4 Add parser robustness tests and a depth cap (row 10)

**Rating: B− — a gap between the stated security policy and the tests.**

**Status: DONE [PR#94](https://github.com/michal-niedzwiedzki/visimark/pull/94)**

#### The problem

`SECURITY.md` explicitly places in scope any document that "hang[s] the process
on input of a reasonable size". But the test suite is entirely example-based:
680 tests, all hand-written cases. There is no fuzzing, no property-based
testing, and no guard against pathological input.

Concretely, `packages/visimark/src/lang/parser.ts` is a recursive-descent Pratt
parser. `parseBp` recurses at lines 79, 108, 116, 126, 158 and 161, with no
depth limit. A formula like `((((((…1…))))))` nested a few tens of thousands
deep will overflow the JS stack. That surfaces as a `RangeError` crash rather
than a clean `LangError` finding — and in the LSP it takes down the server
process, not just one diagnostic.

#### What to do

**1. Cap recursion depth in the parser.** Thread a depth counter through
`parseBp` (or hold it as a `Parser` field, incremented on entry and decremented
on exit). On exceeding the cap, throw the existing `LangError` with the
offending token's span, so it flows through the normal finding path and becomes
an ordinary diagnostic.

Pick a limit far above any legitimate formula but far below the stack limit —
a few hundred is ample; VisiMark formulas are invoice arithmetic, not generated
code. State the reasoning in a comment.

**2. Add a property test.** `bun test` has no built-in generator and the
project has no test-lib dependency — **do not add one**; a small hand-rolled
generator with a fixed seed is more in keeping with the repo's minimal
dependency posture (four runtime deps, all load-bearing). Generate random
well-formed expression ASTs, print them, parse them back, and assert the result
round-trips. This is the same round-trip discipline the `fmt` idempotence tests
already use, extended to the language layer.

**3. Add explicit pathological-input tests:** deep nesting (asserting a clean
`LangError`, not a crash), a very long chain of binary operators, a very long
identifier, and a table with many columns. Each should produce a finding or
succeed — never throw an unhandled error.

#### Constraints

- No new dependencies.
- The depth cap must produce a `LangError` with a valid span, since
  `check`/`build` convert those into positioned findings.
- Confirm the LSP path too: a document with a pathological formula must leave
  `visimark-lsp` responsive. `packages/visimark-lsp/test/diagnostics.test.ts`
  is the right place.

### 2.5 Fix playground bundle staleness (row 13)

**Rating: C — the only finding with a live, user-visible failure. Do this first; it is also the cheapest.**

**Status: DONE [PR#95](https://github.com/michal-niedzwiedzki/visimark/pull/95)**

#### The problem, verified

`docs/vendor/visimark-browser.js` (797 KB, minified) is a **committed build
artifact**. It is produced by:

```
cd packages/visimark && bun run build:playground
```

which no workflow runs. `docs/vendor/playground-data.js` is likewise generated
by `scripts/gen-playground-data.mjs` and likewise never verified.
`.github/workflows/pages.yml` uploads `docs/` verbatim and triggers only on
`paths: ["docs/**"]`.

Nothing connects a change in `packages/visimark/src/**` to a rebuild of that
bundle or to a Pages deploy. **This has already gone wrong.** During the review
I rebuilt the bundle and compared:

- `git diff` shows a 47-line change against the committed copy.
- The committed bundle was last regenerated in `4e66265` (PR #82). `f74dcf4`
  (PR #83) then added the line, area and stacked-bar chart engines.
- Grepping confirms the deployed bundle contains **no `area` and no
  `stacked-bar` engine**.

So the public playground at the project homepage silently runs a pre-#83
engine. A visitor typing `chart x as area of …` gets an unknown-engine error
for a feature the docs say shipped. (User-visible impact is currently limited:
`docs/playground/tutorial/12-charts.md` does not yet use those engines —
only `docs/example-charts.md` and `docs/visimark-design.md` mention them.)

#### What to do

**1. Make CI fail on a stale bundle.** Add a step to the `build` job in
`.github/workflows/ci.yml`, after the existing `bun run build`:

```yaml
- name: the committed playground bundle must match the source
  run: |
    cd packages/visimark && bun run build:playground && cd ../..
    bun scripts/gen-playground-data.mjs
    if ! git diff --exit-code -- docs/vendor/; then
      echo "::error::docs/vendor/ is stale. Run 'bun run --filter visimark build:playground' and 'bun scripts/gen-playground-data.mjs', then commit the result."
      exit 1
    fi
```

Match the house style in that file: a comment saying *why* the step exists —
that the bundle is committed rather than built at deploy time, so nothing else
would catch the drift.

**2. Make Pages redeploy when the engine changes.** Add `packages/visimark/src/**`
to the `paths` filter in `pages.yml`. Without this, even a correctly-rebuilt
bundle might not deploy if the same commit touches nothing else under `docs/`.

**3. Commit the current rebuild** as its own `fix:` commit, so the live
playground actually gains the three missing engines. Keep it separate from the
CI change — one restores correctness, the other prevents recurrence.

#### Consider, and raise with the maintainer

Building the bundle in the Pages workflow instead of committing it would remove
this failure mode entirely. The reason to keep it committed is that
`pages.yml` currently needs no Bun toolchain and no build step. That is a real
trade-off and the maintainer's call — **do not change the deployment model
unilaterally.** Implement the guard, then raise the question.

#### Constraints

- Verify the rebuild is byte-stable: run `build:playground` twice and confirm

### 2.6 Restore lint signal (row 14)

**Rating: C — trivially fixable, and currently the linter is useless.**

**Status: DONE [PR#96](https://github.com/michal-niedzwiedzki/visimark/pull/96)**

#### The problem

`bun run lint` (oxlint) currently emits **1,785 warnings. Every single one
comes from `docs/vendor/visimark-browser.js`** — the 797 KB minified bundle
from §2.5. Source code produces zero warnings.

There is no `.oxlintrc.json` in the repo, so oxlint walks everything. The
formatter already solved exactly this problem: `.oxfmtrc.json` carries
`"ignorePatterns": ["**/*.md", ".vscode/**"]`. Lint just never got the same
treatment.

CI runs `bun run lint`, but warnings do not fail the build — so this is pure
noise rather than a broken pipeline. The cost is that a genuine warning in real
source code is invisible in 1,785 lines of output, and nobody reads it.

#### What to do

**1. Add `.oxlintrc.json`** at the repo root ignoring generated and vendored
output:

```json
{
  "ignorePatterns": ["docs/vendor/**", "**/dist/**", "**/node_modules/**"]
}
```

Check oxlint's current schema for the exact key name before committing —
`.oxfmtrc.json` uses `ignorePatterns`, and oxlint should match, but verify
against the installed version (`oxlint ^1.82.0`) rather than trusting this
snippet.

**2. Confirm the source is genuinely clean** — run `bun run lint` and check the
output is empty.

**3. Give lint teeth.** Once clean, change the root `lint` script to
`oxlint --max-warnings 0` so a new warning fails CI instead of joining the
noise. This is consistent with how the rest of the pipeline behaves: `format:check`,
`typecheck` and `bun test` all already fail hard.

#### Constraints

- Do not silence warnings by adding `oxlint-disable` comments to source. There
  are exactly two suppressions in the entire codebase today
  (`no-control-regex`, in both path gates), each with a one-line justification.
  Keep that bar.
- `dist/` is gitignored but exists locally after a build; ignoring it prevents
  a confusing difference between local and CI lint output.
- If `--max-warnings 0` turns up real warnings in source, fix them properly or
  report them — do not widen the ignore list to make them disappear.

### 2.7 Pin the composite Action's default version (row 18)

**Rating: B− — a supply-chain and reproducibility gap for downstream users.**

#### The problem

`action.yml` exposes a `version` input defaulting to `latest`, and its run step
falls through to:

```bash
npx --yes "visimark@$VISIMARK_VERSION" "$VISIMARK_COMMAND" $VISIMARK_ARGS "${files[@]}"
```

So a consumer writing `uses: michal-niedzwiedzki/visimark@v0.1.3` still gets
whatever `visimark@latest` resolves to at run time — even though they pinned
the Action itself. Two consequences:

- **Not reproducible.** The same commit, re-run next month, can behave
  differently. For a tool whose entire selling point is *proving* numbers
  haven't drifted, an unpinned verifier is an awkward look.
- **Blast radius.** A bad publish breaks every downstream repo simultaneously,
  with no way for a careful consumer to have protected themselves.

#### What to do

Change the `version` input default from `latest` to the concrete current
release (`0.1.3` at the time of review), and document that consumers can set it
back to `latest` if they want rolling updates. Update the `description` to say
what the default means.

Then wire it into the release process so it cannot rot: `docs/releasing.md`
documents the release steps, and `.github/workflows/release.yml` already
derives `ENGINE_VERSION` from `packages/visimark/package.json`. Either add the
`action.yml` default to the release checklist, or — better — add a CI assertion
that `action.yml`'s default equals `packages/visimark/package.json`'s version,
so a forgotten bump fails the build rather than silently pinning consumers to
an old release. The existing CI file has good precedent for this style of
guard.

#### Constraints

- **Do not touch the `command -v visimark` branch.** That escape hatch is what
  lets `.github/workflows/dogfood.yml` run the Action against the current
  branch instead of the published package; there is a long comment in
  `dogfood.yml` explaining the `GITHUB_PATH` wiring that makes it work. Break
  it and the repo starts dogfooding its own last release.
- `$VISIMARK_ARGS` is deliberately unquoted so it word-splits into separate
  flags. Leave it. `"${files[@]}"` is correctly quoted. Do not "fix" either.
- Run the `dogfood` workflow's logic locally or check the next CI run to
  confirm the Action still resolves to the local build.
